Default `dev:local` runs separate simulated v1 telemetry and opt-in synthetic v2 diagnostics. Real mode uses the existing `backend/hardware-server.mjs` startup described in [hardware-demo.md](hardware-demo.md); no startup/provisioning or physical test was performed for this phase.

Existing navigation, demo controls, v1 logs/CSV, chart/map/alert examples and operator authentication are preserved. No dependencies were installed/upgraded. This workspace has no Git metadata, so a Git diff/history could not be used; existing files were inspected before edits. ## Real data export and event history

`GET /api/diagnostics/export.csv` exports **only separate real-v2 storage**, protected by the same operator login/assigned-device ACL as diagnostics. `GET /api/telemetry/export.csv` remains **SIMULATED v1 only**. Real-mode diagnostics provide the download button with explicit limits and errors.

Columns include record/event identity, device, firmware, boot/session, per-type sequence, message/event type, sender UTC/sync status, original backend receipt UTC, uptime, security, acceleration/angular velocity axes, IMU/switch status and faults, lid/mount, source/provenance, durable delivery and accepted identical-retry count/latest retry receipt. Blank cells mean unavailable; zero and false remain literal values. Strings are CSV-escaped and protected against spreadsheet formulas. Numeric negative vectors retain their numeric sign.

Default export limit is 1,000 rows, maximum 10,000. `afterId` continues in ascending durable-record order; response `X-Next-After-Id` supplies the next cursor. `eventsOnly=true` selects events. Exports are bounded chunks, not an unlimited whole-database download or a cross-chunk frozen snapshot. No automatic purge or historical backfill. The schema adds provenance/retry columns to the separate v2 database only; old rows default to REAL DEVICE because they came through that receiver. This label identifies ingress, not physically verified sensor evidence.

`GET /api/diagnostics/events` and the real event panel show latest 100 persisted events. Event identity is `deviceId:sessionId:sequence` within the `tamper_event` discriminator. Retries preserve the original immutable validated payload; reordered JSON keys are equivalent, changed payload at the same identity is rejected. Only accepted identical delivery retries are counted. Offline attempt count, first attempt time and network failures are unknown and are not fabricated. Snapshot history remains bounded to 20 events; CSV can page through older records.

Receiver tests explicitly configure **TEST FIXTURE** provenance on isolated databases. Fixture payloads may use source=device to exercise authenticated ingress, but their export/history provenance never claims physical measurement. Source metadata alone is not authentication; the separate bearer token binds the configured ET-01 identity. Default synthetic diagnostics remain **SIMULATED**.

## Diagnostics, liveness and honest real mode

Device diagnostics show device ID, firmware, active boot/session, latest live sequence/type, uptime, synchronized-clock status and sender UTC. Connection uses the newest accepted **live heartbeat or sensor receipt**: NEVER CONNECTED before any live receipt; ONLINE below 3 configured heartbeat intervals; STALE from 3; OFFLINE from 6. Default heartbeat interval is 5 seconds, giving 15/30-second boundaries. These are provisional software policies, not measured network guarantees.

Browser SSE connection is displayed independently. Rejected messages, duplicate acknowledgements and delayed event delivery never refresh device liveness. Backend restart restores original receipt timestamps; reconnect sends the existing durable snapshot. Sensor report/last-valid-IMU ages retain independent 10/30-second thresholds. Real valid readings may be retained after a fault, explicitly marked OUTDATED, while current sensor faults/unavailability remain visible. No simulated vector substitutes for a missing real vector.

Security displays reported DISARMED/ARMED/TRIGGERED separately from demo controls. Current-boot reports are compared by uptime so late delivery of an older event cannot supersede a later DISARMED sensor report. A report of TRIGGERED means a reported latch, not proof that a siren is currently sounding. Latest received tamper event and persisted history are distinct from fixed example alerts.

In real mode battery, SOC, solar, wind, GPS/location, speed, brake and time-to-empty remain unavailable/not implemented. Charts, map imagery, v1 history and demo controls remain explicitly labeled examples, separate from the real panel. Expanded map is an explicitly fixed simulated example. Browser visual/download checks remain pending.

## Sender clock design

The existing pinned ESP32 core provides SNTP and Preferences; see [Espressif system time](https://docs.espressif.com/projects/esp-idf/en/v4.4.6/esp32/api-reference/system/system_time.html) and [Preferences API](https://docs.espressif.com/projects/arduino-esp32/en/latest/api/preferences.html).

After Wi-Fi connectivity, firmware registers an SNTP success callback and starts UTC `configTime` using configurable primary/secondary servers. Before a valid callback, `sampledAtUtc=null` and `clockSynchronized=false`. Valid system UTC is serialized as an ISO UTC timestamp with milliseconds. A sanity window (2024–2099) and 24-hour callback-age limit gate synchronized status; reboot always clears trust. No timestamp is derived from uptime. Queued event JSON retains its original sender time/sync status; synchronization does not retrospectively invent a time for an unsynchronized event. Backend receipt remains separately assigned UTC.

Live telemetry retains a provisional ±5-second clock-delay budget. Durable historical tamper events allow delayed timestamps, reject future timestamps more than 5 seconds ahead, and never become live telemetry. SNTP is not authenticated time; accuracy, drift, network availability and the chosen delay/trust thresholds need later device evaluation. Firmware does not claim calibrated UTC accuracy or physical connectivity.

## Durable event spool

Firmware stores immutable event JSON in **8 Preferences/NVS slots**, each at most 1,023 JSON bytes plus header/CRC. Each append checks committed write size and rereads the blob. Slots include format magic, length and CRC32; damaged/wrong-type slots are quarantined and never automatically overwritten or purged. Storage full/write failure logs an explicit warning and uses the existing 16-entry RAM retry queue plus pending entry. RAM fallback is not reset durable; exhausted RAM logs loss. Local alarm logic remains independent of network connectivity, with the existing independent siren cutoff timer preserved.

Networking retries up to one NVS and one RAM event per 5 seconds. NVS selection rotates to avoid a single rejected event blocking every other slot. Only an exact HTTP 202 JSON acknowledgement containing accepted=true and durable=true permits deletion. Failed delete keeps the event for an idempotent retry. Network/storage access is serialized; flash persistence happens in the local event path before network delivery. Flash-write latency has not been measured. A reset during persistence, physical NVS endurance, full/corrupt physical flash, independent cutoff timing and actual power-loss behavior remain **UNVERIFIED**.

Backend event acceptance is separate from live boot/sequence reduction. Historical events from an old or otherwise unseen boot may be stored under their original identity by the token-bound device. They do not activate a boot, retire a live boot, change sensor readings/order or refresh live receipts. This deliberate historical-ingress policy allows recovery after either side restarts; no synthetic backfill occurs. Same-identity conflicts are rejected; logical deduplication relies on firmware preserving identity. New live boots still require sequence-zero heartbeat, with retired live boots rejected. UUIDs and bearer credentials do not prove physical boot chronology or prevent captured-LAN replay.
