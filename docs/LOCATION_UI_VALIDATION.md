# Location explorer, location history and recorded GPS track

Updated 25 October 2026. Frontend only; existing authentication, role permissions, API contracts and database behavior are preserved.

The Location page uses a larger interactive map, a floating vehicle identity card, a translucent Location History timeline and a last-reported-position card. Recorded GPS polylines, numbered stop-duration markers and stop-to-stop distance labels appear on the map. Fit track frames recorded points; a checkbox shows/hides the historical layer. Existing vehicle selection, city-reference controls, fleet framing, GPS markers, basemap failure messaging, refresh and vehicle-details navigation remain available. Bottom navigation remains unchanged.

The recorded-track treatment uses SOLAIR blue with a contrasting outline, an amber latest-point pin, a blue start marker and a softened blue-tinted basemap. The history map has a taller responsive viewport when points are available. Fit track leaves room for controls, endpoints and badges; native map resizing preserves its geographic center. The duration beside each distance is the recorded interval between stops, not an arrival-time estimate. Start/latest markers identify the loaded history window, not an asserted complete trip or destination. Actual GPS geometry and gaps remain unchanged, and OpenStreetMap attribution stays visible.

Location History uses the existing authenticated `/api/history/:vehicleId?mode=...&offset=...` endpoint. Initial load/manual refresh pages through at most 500 reports, stopping early when a page has fewer than 100. Polling every 30 seconds loads the latest 100 and merges/deduplicates the bounded 500-report cache. No backend behavior changed. The UI shows up to six detected stops, newest first. Stops require at least three distinct fresh GPS fixes within 60 metres of the initial point, spanning the selected minimum duration (1, 2, 5 or 10 minutes; default 2). Missing/stale fixes and gaps over five minutes break observations. Duplicate frames/cached fix timestamps do not extend the interval. Wrong-mode, recovered historical CPE, event-only, malformed and future-dated records are excluded.

These are inferred observations, not confirmed visits or continuously verified parking durations. First/last recorded timestamps include year and seconds, explicitly using Asia/Manila (UTC+8); they are not asserted arrival/departure times. This is a recent sample window, not complete travel history. Demo observations are labeled simulated and do not appear in hardware mode. Selecting a stop brings its historical area into view; returning restores the vehicle's last known position or city reference.

Track segments break at missing fixes, gaps over five minutes or point-to-point jumps implying speeds over 120 km/h (a corruption guard, not a vehicle speed claim). Distances use great-circle distances summed along consecutive recorded points. A leg runs from the previous stop's last observation to the next stop's first observation. If that window has any missing/unreliable segment, its distance is unavailable; no line or distance bridges the gap. The track summary totals only recorded continuous sections, and a window with no measured segment shows unavailable rather than a misleading zero. These are GPS estimates, not road-network routing, map-matched paths or odometer readings.

Address lookup was explicitly deferred by the user. Stop cards show “Address unavailable” and coordinates. No street address, city address or confirmed place name is fabricated. No geocoding service, new dependency, database table or backend endpoint was added. Future integration should resolve authorized stored stop coordinates through an authenticated backend, return address/provider attribution and matching-quality information, cache results and preserve unavailable/error states. Reverse-geocoded matches must not be described as guaranteed exact addresses. Saved favorites, a complete travel archive and authoritative arrival/departure records remain separate backend/product work.

Validation uses eight focused unit tests for stop inference, duration thresholds, route/leg distances, missing segments, bounded history and Manila timestamps. The isolated browser fixture covers empty hardware history, inferred stops, track polylines, map labels, fit/toggle controls, duration filtering, address-unavailable states, selection/return, refresh retention, history failure/retry, mode separation and responsive light/dark layouts at 320, 360, 390 and 1440px. GPS records and basemap tiles are explicitly synthetic and never written into the working database. Actual-phone usability and physical GPS accuracy remain unverified.

Results: all eight unit tests, the Location browser fixture and existing map regressions passed. Map regressions cover desktop/mobile BEMAC/Manila, NWOW/Malabon, vehicle switching, GPS priority, first-fix behavior, preserved zoom, invalid coordinates and unassigned references. The older map test now uses an exact vehicle-selector label and passes through the mobile welcome screen. Production build, TypeScript and lint passed. The live phone proxy also rendered the new Location page for the existing assigned demo account; insufficient hardware GPS history correctly showed an empty stays list.
